  <action>
    Per D-13, install the authorizer for the whole connection lifetime, enable query-only and defensive settings where bound, disable trusted schema where compatible, keep extension loading disabled, and pair the policy with statement-readonly. Implement `PolicyContext` as the closed discriminated union `{kind:'user'}`; `{kind:'catalog.bootstrap', statement:'function-list'|'table-list'|'schema-objects'|'schema-version'}`; `{kind:'catalog.object', statement:'table-xinfo'|'foreign-key-list'|'index-list'|'index-xinfo'|'trigger-list'}`; or `{kind:'query.explain'}`. The dispatcher, not caller SQL, assigns these source-controlled statement IDs; there is no boolean/trusted bypass.

    Build the function policy by executing the one fixed internal `PRAGMA function_list` statement once for each new real connection before accepting user commands, under `catalog.bootstrap/function-list`, with the authorizer already installed. Validate and bound its exact `name,builtin,type,enc,narg,flags` rows, ASCII-casefold names, group every overload, and freeze the resulting set for that connection. A name is eligible only when at least one row exists, every overload has `builtin=1`, every type/encoding/arity/flag field has the pinned-package documented shape, no row has `SQLITE_DIRECTONLY`, and no flag bit falls outside the pinned SQLite header's encoding bits plus `DETERMINISTIC`, `SUBTYPE`, `INNOCUOUS`, `RESULT_SUBTYPE` and `SELFORDER1` mask. The exact deny-name set is `load_extension`, `readfile`, `writefile`, `edit`, `shell`, `eval`, `fts3_tokenizer`, `sqlite_log`, `sqlite_rename_column`, `sqlite_rename_table`, `sqlite_rename_test`, `sqlite_rename_quotefix` and `sqlite_drop_column`; deny these even if a future build marks them built-in. Also deny every `builtin=0`/application-defined, shadowed, malformed, unknown-flag or absent name. Record a stable hash and row count of the validated function-list policy in test evidence without logging database data. This runtime-derived rule is mandatory; the executor must not substitute a hand-selected function list.

    Encode the authorizer as an exhaustive action/field table. `SQLITE_SELECT` and `SQLITE_RECURSIVE` require their documented first three unused callback fields to be absent and permit the source field only when null or a bounded main-schema view/CTE source observed in the pinned binding. `SQLITE_READ` requires database exactly `main`, a non-empty bounded table name and a null or bounded source name; its column is either a bounded non-empty name, exact callback `ROWID` (cover SQL aliases `rowid`, `_rowid_`, `oid`), or SQLite's documented empty string for a no-column table read such as `count(*)`. For `sqlite_schema`/`sqlite_master`, allow only empty string or `type,name,tbl_name,rootpage,sql`, never rowid or an unknown column. `SQLITE_FUNCTION` requires the documented unused first field to be absent, a bounded normalized name in the frozen eligible set, and only null/bounded source fields produced by direct SQL or a main-schema view. For user/query-explain PRAGMAs, the no-argument set `table_list,schema_version,user_version,application_id,page_count,page_size,freelist_count,encoding` requires null/empty argument; the object-argument set `table_info,table_xinfo,foreign_key_list,index_list,index_info,index_xinfo` requires one non-empty bounded identifier argument; all auxiliary callback fields must match the pinned binding contract. Thus an argument to `user_version`, `application_id`, `page_size` or another value-setting PRAGMA is denied. Catalog contexts admit only the action/field rows required by their exact fixed statement ID and bound object argument, including `function-list` only during connection bootstrap. Deny every write/schema/transaction/savepoint/attach/detach/vacuum/analyze/reindex/vtable action and every unknown action/context/statement ID/field shape. Use SQLite prepare/tail/bind-count validation; keep the authorizer installed through prepare, step and automatic reprepare, and finalize every rejected handle. Adding any function rule, PRAGMA, action or catalog statement ID requires a decision-table row, real-WASM allow/deny/recovery test, threat note and regression test.
